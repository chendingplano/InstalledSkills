## Independence

Author the benchmark independently of `extract_metrics` predictions. Do not call the processor or preview extraction API, copy `kb.metrics`, or read its predictions until the benchmark is frozen. Production records are predictions, not ground truth. Do not inherit the older `document-metric-extractor` skill's precision-over-recall policy or legacy file/storage schema.

Recall and precision are both required. A benchmark that over-includes understates the extractor's recall exactly as one that under-includes overstates it. When in doubt, apply the gate (§2.1); do not include something just because it uses 应 ("shall").

## 2. Make a full-document candidate inventory

Read every source line, including appendices, tables, notes, equations and headings. For long documents use bounded windows with surrounding context, tracking which original line IDs have been read; return to complete evidence before deciding boundary-spanning assertions. Search is a second-pass discovery aid, never a replacement for reading the document.

Build two ledgers in the payload:

- `coverage`: non-overlapping source ranges covering every line, with section/table-specific review notes, including regions with no metrics.
- `candidates`: each plausible assertion with a stable local ID, exact spans, disposition (`accepted`, `excluded`, `duplicate`, or temporarily `uncertain`), **`rule_id`** (the rule below that decided it), rationale and final metric IDs. A single line/table can have many candidates; line coverage alone is insufficient.

`rule_id` must be one of the bold IDs in this file: an accepted candidate cites an `A` rule, an excluded one an `X` rule, a duplicate **D1**. The rationale says how the rule applies to this text.

### 2.1 The metric gate

A candidate is a metric only if the source names all three of:

- **(a) an object**: a thing, facility, vehicle, container, equipment, product, material, sample or test. An activity counts as the object only when the requirement is a number about it (for example "每月至少检查2次"); then record that the object is unspecified. An activity whose time or frequency is to be agreed, set or announced is excluded (X2).
- **(b) a measurable property of that object**: a quantity, something with a value on a unit or scale, such as a mass, concentration, ratio, rate, frequency, duration, temperature or a count of the object's parts. The time slot or clock time at which an activity takes place (收运的时间, "collected in the morning") is a schedule, not a measurable property. A feature or state that is only checked, not measured (has a lid, fully enclosed, no odour, intact), is not a measurable property (X15).
- **(c) a value, bound or range** for that property, **stated by this document**. There is no stand-in: a quantity whose value is left open (to be declared, agreed, or set or sized by another factor or by design), a quantity only listed to be measured or recorded, and a formula or definition of how the value is computed all have no value and are excluded as X18 (§3.2). Delegating the criterion to a cited document is X16: the value exists, but in that document.

Test the clause, not its keywords. Ask: "What would an inspector measure, on which object, and what number passes?" If any of the three answers is missing from the source, the candidate fails the gate. **A metric has at least a value**: when in doubt whether a candidate with a value is a metric, accept it; when it has no value, it is not one. A requirement that passes every part except that it has nothing to measure is still a real requirement, but it belongs to the provisions, not the metrics (ADR 2026100603 DR3); record it as X15 or X16, not as a lesser exclusion.

### 2.2 Accept rules

| Rule | Accept when | `value_range_type` / `value_class` |
|---|---|---|
| **A1** | A numeric value, bound, range or tolerance of a property of an object, including counts, frequencies, ratios and rates. Also when the clause names a quantity whose limit lives in the cited document. See §2.4. | 收运过程应符合 CJJ 184; 堆肥应符合 CJJ 52; 粪大肠菌群数应达到 NY884 的要求 |


X17 (sizing duty, 4.x) is retired; its candidates are X18. Do not cite it.

**D1** marks a repeated detection of the same occurrence, or a pointer that states no value (see §3, Occurrences). A restatement at another location is not D1: it is an occurrence of the retained metric.

A candidate that fails §2.1 but fits no X rule is not a reason to accept it. Keep it `uncertain` and resolve it before saving; if it reveals a gap in these rules, report it in `limitations` and do not save.

### 2.4 Pure requirements (X15, X16)

X15 and X16 are the two kinds of requirement that `extract_metrics` drops and logs (`kb.doc_proc_logs`, activity `exclude_pure_requirements`, kinds `inspection_requirement` and `delegated_requirement`). Record them with the same care as accepted rows, because the ledger is the answer key for that log:

- one candidate per requirement, split as an accepted row would be split (§3): "anti-odour, anti-spill, anti-leak" is three X15 candidates; a clause citing two documents for two properties ("处理技术应符合 CJJ 90，污染控制应符合 GB 18485") is two X16 candidates;
- exact `source_line_spans`, and a `reason` that names the object (or process) and the inspected feature or the delegated property;
- for X16, the reason also names each cited document as the normative-reference list writes it, with a space between the code and the number (`NY 884`, even where the clause prints `NY884`).

They link no metric. Do not import values from a cited document to turn X16 into A1. Not X16: a normative-reference list alone (X14); a numeric requirement that cites a document only for its test method (A1, an ordinary numeric metric); a delegation with permissive modality (X8); one to an unnamed requirement (X9); a pointer to another clause or table of the same document (D1 of the rows it points to, or the X rule of what it points to).

### 2.5 Data dictionaries (6.3.0)

A data dictionary, data-element catalogue, message or dataset specification gives, for each data
element (a field), attributes such as its data type, data format, value domain, unit, obligation
(M/O/C) and allowed occurrences. The **data element is the object** (gate (a)); the subject is the
data element, named by its name and identifier ("数据元“身高”（2010010）"). Decide each attribute of
each element:

| Attribute | Rule | Row |
|---|---|---|
| **Data format** with a number ("a..50", "an18", "n2", "n4..5,1", "n..6,1") | **A1** | **One row per element** holding the whole format; never split length and decimal places into two rows. `metric_value` = the format as the notation writes it; `metric_unit` = the document's unit of length (位, characters); `value_range_type` from the length part: fixed length (`an18`, `n3,1`) is `exact`, a maximum only (`a..50`, `n..4,1`) is `upper_bound`, a minimum and maximum (`n4..5,1`) is `range` with `value_min`/`value_max` the two lengths. The decimal places stay in `metric_value` and are spelled out in `threshold_or_target` and `metric_desc`. `value_class = requirement`; tag `data_format` |
| **Data format** with no number (YYYYMMDD, a date or time pattern; an empty format of a boolean) | **X3** | none: it names a notation, it states no number in the row. Do not borrow a length from an example elsewhere in the document |
| **Allowed occurrences** ("1", "0..1", "0..4", "1..n") | **A1** | One row per element: `1` is `exact` 1; `0..4` is `range` 0–4; `1..n` (no upper limit) is `lower_bound` 1. `metric_unit` 次 (times per instance); `value_class = requirement`; tag `occurrence_count` |
| **Obligation** M / O / C | none of its own | It is the occurrence count read another way; do not make a row. A C element's stated condition ("受检者为女性时必选") is applicability of the obligation, not of the occurrence range: quote it in the occurrence row's `threshold_or_target`, leave `condition` empty |
| **Value domain**: code list or enumeration ("1——正常；2——黄染", "Y——异常；N——正常", "见表5"), and the code tables themselves | **X3** | none: codes and their meanings define terms. A code meaning that states a value of a named quantity (采血时间代码 "2——口服葡萄糖后30min") is A1/A6 for that value (the aggressive reading of a number inside a definition, X3) |
| **Value domain** delegated to an identified document ("采用 GB/T 2659 中的…代码") | **X16** | none |
| **Unit** of a measured element ("cm" for 身高) with no value | part of the element's **X18** candidate | none: the element's measured value is not stated |
| **Definition** column (说明) | **X3** | none, except a number in it that is a value, limit or condition of a named quantity (X3) |
| **Identifier**: the document's own numbering of its data elements ("内部标识符采用七位数字编码", group ranges 1000000～1999999) | **X14** | none: document codes |

Notation clauses (what "a", "n", "an", "..", "p,q", M/O/C mean, with their examples) are X3. Record
in the ledger one candidate per element and attribute (format, occurrences, value domain, measured
value), so the ledger accounts for every row/attribute pair. When the printed format is a misprint
that the document's own notation makes unambiguous (a letter `l` for the digit `1`, a full stop for
the decimal-place comma), store the notation's reading in `metric_value`, quote the printed text in
`evidence`, and say so in `annotation_notes`.

## 3. Resolve each assertion and its context

One row represents one property of one subject under one condition, with its stated value or requirement.

**Splitting.** Split a sentence only into parts that **each pass the gate (§2.1) on their own**. Split distinct properties (total As, Hg and Pb in one table row are three metrics). Excluded pure requirements are split the same way (§2.4). Do not split a conjunction of vague adjectives into several rows; if the whole fails the gate, it is one excluded candidate. Never split formula operands from their formula. Split table cells/rows when conditions, objects or measured properties differ: a table giving one property for several conditions (SC1, SC2, SC3) is one row per condition, each with its condition, never one row holding several values ("25; 25; 35"). Preserve a single interval/tolerance as one assertion. Never combine a value from one row with a subject/unit from another.

The subject is a source-supported object, facility, product, sample or test. If only an activity is named in a numeric requirement (for example, "每月至少检查2次"), use that activity as the subject and note that its object is unspecified. Do not attach it to a nearby object without evidence. If neither a subject nor activity can be established from the source/context, retain the candidate as uncertain rather than fabricating a subject.

For each table reconstruct multi-level headers, units, row labels, rowspans/colspans, captions, footnotes, merged cells and continued tables before annotating values. A whole HTML table may occupy one source line. Keep its line ID unchanged and record logical data row IDs in `source_table_rows`. Follow `ParseTableGrid` in `ChenWeb/server/api/doc-processing/table_grid.go`: header IDs `h0`, `h1`, ...; data IDs `r1`, `r2`, ... . Cite data rows in stored metrics. Use the existing parser when header/span semantics are complex; do not guess row IDs or hashes. Preserve source HTML substrings as evidence, optionally adding human-readable row text to notes. Enumerate every applicable row/property pair in the candidate ledger.

Use minimal supporting spans plus any header, note or definition needed to interpret the assertion; discontinuous spans are allowed. Normalize spans as strings `"N"` or `"N:M"`, sorted with overlaps/adjacency merged. Never write `"N-M"` or `"116#r1"` into `source_line_spans`. Record exact, nonempty source substrings with original line IDs in `evidence`; an excerpt can support several independent metrics.

Preserve subject, value, comparator, unit, scale, frequency, scope, exceptions and negation. Keep decimal precision, inequalities, ± tolerances, scientific notation, percentages and ratios in source-faithful text. Do not invent zero, units or thresholds for absent data. For ratios written `N:1`, the contract's unit is `ratio`. Ranges additionally carry numeric `value_min`/`value_max`; other range types leave those fields null. Tolerances/approximations not losslessly expressible by the enum retain exact wording and interpretation notes; never rewrite them into different acceptance criteria.

**Bounds and comparators.** `metric_value` holds the bare number only, never a comparator (`100`, not `<100`). The one exception is the symmetric tolerance sign **±**: it is part of the value, not a comparator, so keep it. A tolerance, uncertainty or permitted deviation written `±x` (`±0.2 K`, `±1%`, `测量不确定度：±0.5%`) is stored as `metric_value = "±x"` (`±0.2`), never as the bare `0.2`, with `value_range_type = upper_bound` (the bound on the magnitude, |deviation| ≤ x) and the unit in `metric_unit`. Do not drop the ± on the grounds that `upper_bound` implies it, and do not store an asymmetric tolerance (`+0.2/−0.1`) or an interval `a±b` this way: `a±b` stays `range` with the value as written (`20±5`). The comparator lives in `value_range_type` and in the source wording of `threshold_or_target`. Inclusive bounds (≥, ≤, 不小于, 不大于, 不低于, 不超过, 以上/以下 where the standard defines them as inclusive) use `lower_bound`/`upper_bound`. A **strict** bound (>, <, 大于, 小于, 低于, 超过) uses the same `lower_bound`/`upper_bound` and adds the reasoning tag `strict_bound`.

**`value_class = definition`** is for interpretation cut-offs only (A1 with the tag `interpretation_bound`, `formula_or_definition` holding the reading). A formula or a definition without a value is X18, a term definition X3, an applicability descriptor X5.

**Conditions.** `condition` holds everything the source states that limits when, where, for whom or how the value holds, in its words or a faithful paraphrase. Read it broadly:

- applicability: the population, user group, category, size class, model, variant or grade the value is for (适用人群：幼儿; 称量≤50 kg; Class A);
- environment and operating state (环境温度 20 ℃±5 ℃; 正常使用时; at rated load);
- the test method, apparatus or arrangement used to obtain or check the value (采用运动模拟装置; 用模拟物往复模拟运动; method B);
- the location, part or body site (测量部位：四肢; at the outlet);
- a load, input level, frequency, time point or stage (在 1 kHz 下; after 1 000 cycles).

`metric_subject` names only the object; every qualifier above goes in `condition`, never in the subject. Write the condition as labelled qualifiers `<kind>：<value>` joined by `；` (source language; `<kind>: <value>` joined by `; ` for English sources). A table column or sub-header that qualifies a row is a stated condition of every value in that row. Never infer a condition from context (for example "when a compliant treatment system is used" when the source says no such thing). Three things that look like conditions are not:

- **Suitability of a method or mode** ("适用范围: 人口密度高的农村地区"). It says where a mode is a good choice, not when the requirements of that mode apply; the mode itself belongs in `metric_subject`. Leave it out of `condition`. A real scope limit stated with a metric remains a condition of that metric; a scope limit of an excluded requirement (容积在50立方米以下的户用沼气池 for the NY/T 90 delegation) has no row to attach to and stays X5.
- **Measurement basis** (以烘干基计, 鲜样, dry basis, as received). It says how the value is measured. Put it in `metric_name` or `metric_desc` and keep it in `threshold_or_target`; not in `condition`.
- **The object itself, the comparator or a cited document.** They belong in `metric_subject`, `value_range_type` and the X16/`threshold_or_target` text.

**Schedules.** A frequency is a count per period. "每日/daily" is `exact`, `metric_value` `1`, `metric_unit` `次/日` (or `times/day`), with the source wording in `measurement_frequency`; "至少每日/at least daily" is `lower_bound`. Do not encode it as an interval of 1 day.

Match source language in core text fields. For English, leave `_en` fields empty/null. Translate non-English companion fields faithfully after checking the assertion. Categories are nonempty semantic keys, not paths: reuse existing keys through read-only lookup where appropriate; otherwise annotate an explained key locally without creating production categories or invoking indexing workflows.

**Occurrences.** The same metric (same subject, property, value, unit, comparator, condition and claim class) is often stated in more than one place: a definition, the requirement, a table, a later clause that restates it. That is one metric, not a duplicate:

- store **one row**; its `source_line_spans` list the lines of **every** occurrence (normalized, discontinuous spans allowed) and `source_table_rows` the union of the table rows involved; keep one `evidence` entry per occurrence line, and make `threshold_or_target` the clearest statement. Set `location_type` to `mixed` when the occurrences are of different kinds (sentence and table);
- the ledger keeps **one candidate per occurrence**, each `accepted` under the same `A` rule, with `metric_ids` naming that one metric, and a rationale that says "same metric as <candidate>, restated in <clause>". Do not mark a later occurrence D1;
- the metric is the same only when **everything** matches. A different subject (the nominal airflow and the nominal fan power are both measured at 1013.25 hPa), property, value, unit, comparator or condition is a different metric and keeps its own row. Do not merge by name, number or line alone, and do not merge different conditions. Two clauses that state the same settings with different test methods or apparatus (6.5.14.1 with a 运动模拟装置, 6.5.14.2 with a 模拟物) are two metrics per setting, each with its method as condition;
- a vague restatement of a property that another row states concretely (a slogan "日产日清" beside "collected daily") is excluded under its X rule, not merged.

**D1** is only for (a) the same occurrence detected twice by overlapping reading windows, and (b) a pointer to another clause or table that states no value of its own ("见表 2", "按 5.4 的规定"); the value stays with the row that states it. A restatement that carries the value itself is an occurrence, not D1.

### 3.1 Statement kind

Every accepted metric carries exactly one reasoning tag `kind:<kind>` saying what the row is to a domain expert (ADR 2026100603). The application labels rows with the same vocabulary, so the gold kind is also the expected label.

| Kind | Rule and shape |
|---|---|
| `requirement_with_criterion` | A1 with `value_class` `requirement` or `target` |
| `test_parameter` | A6 (`test_condition`) |
| `metric_definition` | A1 interpretation cut-offs (`interpretation_bound`) |
| `metric_value` | A1 with `value_class` `observation` or `design_capability` |

The application's other kinds never describe an accepted row under these rules: `inspection_requirement` is X15, `delegated_requirement` is X16, a non-numeric `observation` is X15, a term `definition` is X3, `requirement_value_open` is X18. Consequently no accepted row has `value_class = reference` or `metric-with-no-value`, the tag `external_reference` or a `cited_doc:` tag, and **no accepted row is `qualitative` or `limit_absent`**: every accepted row states a value.

`validate` derives the kind from `value_class`, `value_range_type`, `formula_or_definition` and the tags, using the same rules as the application, and refuses a row whose `kind:` tag disagrees. A disagreement means the row's representation is wrong (for example an interpretation cut-off stored as a requirement), not that the tag should be changed to match. `metric-with-no-value` (4.1.0–5.1.0) is not used.

### 3.2 Candidates with no value (X18)

Record every X18 candidate in the ledger with the same care as an accepted row, because `extract_metrics` sets such rows aside with reason `no_value` and the ledger is the answer key for them:

- one candidate per named quantity, split as an accepted row would be split (§3): "设备应明确主体工艺、比能耗、发酵周期等运行技术参数" gives X18 candidates for 比能耗 and 发酵周期 (主体工艺 is X13);
- exact `source_line_spans`, and a `reason` that names the object, the quantity and why no value is stated (to be declared by whom, agreed between whom, sized by what factor, listed to be recorded, or computed by which formula);
- a formula is one X18 candidate; its operands are not separate candidates (X13).

They link no metric. Do not supply a typical value, a value from another document, or a value computed from a formula to turn X18 into A1. Not X18: a quantity whose value another clause or table of this document states (an occurrence of the row that states it, or D1 when the clause only points to it), a delegation to a cited document (X16), an activity's agreed time or frequency (X2), a definition (X3), a provision with no named quantity (X7).

## 4. Audit completeness, correctness and consistency separately

Perform all three reviews against the source after drafting:

1. **Completeness:** re-read each section/table without relying on drafted metrics. Enumerate measurements/property requirements again; reconcile every candidate with final rows or an explained exclusion. Recheck conjunctions, cross-line clauses, continued tables, footnotes, formulas, header units, numeric words, inspection requirements and delegated requirements (each one an X15/X16 candidate, §2.4). Account for every data-row/property pair and all original lines.
2. **Correctness:** verify every saved field against cited lines. Check subject-to-value association, operators/negation, units/scales, row/column assignment, ranges/tolerances, frequency, applicability, translations and duplicates. In addition:
   - every accepted row passes the gate (§2.1) and its `rule_id` matches its `value_range_type`/`value_class` and tags;
   - every non-empty `condition` appears in the source (no invented applicability), is written as `<kind>：<value>` qualifiers, and every stated qualifier (population column, sub-header, environment, method or apparatus, location, load) of the value is in it, not in `metric_subject`;
   - every `threshold_or_target` states the requirement on its own, readable without the row's other fields (not a fragment such as "种名");
   - `metric_value` holds no comparator; strict bounds carry `strict_bound`;
   - every row has one `kind:` tag that matches its rule (§3.1), and none is an inspection or delegated requirement;
   - every accepted row states a value from this document (no `qualitative` or `limit_absent` row, no `metric-with-no-value`); every value-less named quantity is an X18 candidate (§3.2);
   - no accepted row is a definition, a symbol explanation or a count of the document's own parts (X3, X4), and no row has a quantity the clause does not name (X7);
   - every table that gives one property for several conditions has one row per condition;
   - no `condition` holds a method's suitability or a measurement basis (§3, Conditions).
   - in a data dictionary, every element with a numeric data format has one format row (the whole format, not split) and every element has one occurrence row; no format, occurrence or obligation was excluded as a definition (§2.5).
   Exact excerpt validity and high confidence do not prove semantic correctness.
3. **Consistency:** list the metrics that share subject, property, value, unit and condition; each such group must be one row with all its lines (§3, Occurrences). Check that every occurrence candidate cites lines contained in its metric's `source_line_spans`, and that no value stated in prose or a table was excluded as an operand of a formula that encodes it (X13). Then group candidates by source line and by `rule_id`. For every excluded candidate, check that no accepted candidate on the same line (or with the same wording elsewhere) relies on the reasoning the exclusion rejected, and the reverse. Equivalent clauses must receive the same rule. Resolve each conflict by re-deciding both candidates, not by editing rationales. Then compare the accepted count with the number of distinct gate-passing assertions you would expect from the document's structure; no accepted row may be `qualitative` or `limit_absent`. Check the X15/X16 candidates the same way: equivalent clauses (two vehicles "shall be enclosed", two processes "shall comply with" a standard) get the same rule, and an X15/X16 candidate is not also hidden as an accepted row. Equivalent value-less clauses (declared, agreed, sized "根据…合理设置", "与…相适应", "by design", listed to be recorded, formulas) all get X18.

Describe concrete checks/findings in `completeness_review` and `correctness_review`; put the consistency findings in `correctness_review` under a "Consistency:" heading. Resolve all uncertain candidates; never relabel uncertainty as exclusion merely to pass validation. If parser damage, missing context, a rules gap or contract ambiguity remains, retain draft JSON and identify it in `limitations`. Do not publish an incomplete/unresolved set as a complete benchmark. Distinguish completeness within the line file from original-PDF coverage; image-only or omitted content requires a stated limitation and appropriate review.
