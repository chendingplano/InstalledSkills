## Independence

Author the benchmark independently of `extract_metrics` predictions. Do not call the processor or preview extraction API, copy `kb.metrics`, or read its predictions until the benchmark is frozen. Production records are predictions, not ground truth. Do not inherit the older `document-metric-extractor` skill's precision-over-recall policy or legacy file/storage schema.

Recall and precision are both required. A benchmark that over-includes understates the extractor's recall exactly as one that under-includes overstates it. When in doubt, apply the gate (§2.1); do not include something just because it uses 应 ("shall").

## 2. Make a full-document candidate inventory

Read every source line, including appendices, tables, notes, equations and headings. For long documents use bounded windows with surrounding context, tracking which original line IDs have been read; return to complete evidence before deciding boundary-spanning assertions. Search is a second-pass discovery aid, never a replacement for reading the document.

Build two ledgers in the payload:

- `coverage`: non-overlapping source ranges covering every line, with section/table-specific review notes, including regions with no metrics.
- `candidates`: each plausible assertion with a stable local ID, exact spans, disposition (`accepted`, `excluded`, `duplicate`, or temporarily `uncertain`), **`rule_id`** (the rule below that decided it), rationale and final metric IDs. A single line/table can have many candidates; line coverage alone is insufficient.

`rule_id` must be one of the bold IDs in this file: an accepted candidate cites an `A` rule, an excluded one an `X` rule, a duplicate **D1**. The rationale says how the rule applies to this text.

### 2.1 The metric gate

A candidate is a metric only if the source names all three of:

- **(a) an object**: a thing, facility, vehicle, container, equipment, product, material, sample or test. An activity counts as the object only when the requirement is a number about it (for example "每月至少检查2次"); then record that the object is unspecified. A4's stand-in for (c) does not count as such a number: an activity whose value is left open, agreed, to be declared or to be set has no object, and the candidate is excluded (usually X2).
- **(b) a measurable property of that object**: a quantity, something with a value on a unit or scale, such as a mass, concentration, ratio, rate, frequency, duration, temperature or a count of the object's parts. The time slot or clock time at which an activity takes place (收运的时间, "collected in the morning") is a schedule, not a measurable property. A feature or state that is only checked, not measured (has a lid, fully enclosed, no odour, intact), is not a measurable property (X15).
- **(c) a value, bound or range** for that property, or the one stand-in: the document names the quantity as something that must have a value and leaves that value open, to be declared, agreed, or set or sized according to another factor or by design (A4). The row is then a metric with no value (§3.2). Delegating the criterion to a cited document is not a stand-in (X16): the value exists, in that document.

Test the clause, not its keywords. Ask: "What would an inspector measure, on which object, and what number passes?" If any of the three answers is missing from the source, the candidate fails the gate. A requirement that passes every part except that it has nothing to measure is still a real requirement, but it belongs to the provisions, not the metrics (ADR 2026100603 DR3); record it as X15 or X16, not as a lesser exclusion.

### 2.2 Accept rules

| Rule | Accept when | `value_range_type` / `value_class` |
|---|---|---|
| **A1** | A numeric value, bound, range or tolerance of a property of an object, including counts, frequencies, ratios and rates. Observations, targets and design capabilities keep their actual claim class. An **interpretation cut-off** (a value that says how to read a result, such as "GI < 100% means the compost is phytotoxic") is not a requirement: store it with `value_class = definition`, the reading in `formula_or_definition`, and the tag `interpretation_bound`. | numeric / as stated (`definition` for interpretation cut-offs) |

### 2.4 Pure requirements (X15, X16)

X15 and X16 are the two kinds of requirement that `extract_metrics` drops and logs (`kb.doc_proc_logs`, activity `exclude_pure_requirements`, kinds `inspection_requirement` and `delegated_requirement`). Record them with the same care as accepted rows, because the ledger is the answer key for that log:

- one candidate per requirement, split as an accepted row would be split (§3): "anti-odour, anti-spill, anti-leak" is three X15 candidates; a clause citing two documents for two properties ("处理技术应符合 CJJ 90，污染控制应符合 GB 18485") is two X16 candidates;
- exact `source_line_spans`, and a `reason` that names the object (or process) and the inspected feature or the delegated property;
- for X16, the reason also names each cited document as the normative-reference list writes it, with a space between the code and the number (`NY 884`, even where the clause prints `NY884`).

They link no metric. Do not import values from a cited document to turn X16 into A1. Not X16: a normative-reference list alone (X14); a numeric requirement that cites a document only for its test method (A1, an ordinary numeric metric); a delegation with permissive modality (X8); one to an unnamed requirement (X9); a pointer to another clause or table of the same document (D1 of the rows it points to, or the X rule of what it points to).

## 3. Resolve each assertion and its context

One row represents one property of one subject under one condition, with its stated value or requirement.

**Splitting.** Split a sentence only into parts that **each pass the gate (§2.1) on their own**. Split distinct properties (total As, Hg and Pb in one table row are three metrics). Excluded pure requirements are split the same way (§2.4). Do not split a conjunction of vague adjectives into several rows; if the whole fails the gate, it is one excluded candidate. Never split formula operands from their formula. Split table cells/rows when conditions, objects or measured properties differ. Preserve a single interval/tolerance as one assertion. Never combine a value from one row with a subject/unit from another.

The subject is a source-supported object, facility, product, sample or test. If only an activity is named in a numeric requirement (for example, "每月至少检查2次"), use that activity as the subject and note that its object is unspecified. Do not attach it to a nearby object without evidence. If neither a subject nor activity can be established from the source/context, retain the candidate as uncertain rather than fabricating a subject.

For each table reconstruct multi-level headers, units, row labels, rowspans/colspans, captions, footnotes, merged cells and continued tables before annotating values. A whole HTML table may occupy one source line. Keep its line ID unchanged and record logical data row IDs in `source_table_rows`. Follow `ParseTableGrid` in `ChenWeb/server/api/doc-processing/table_grid.go`: header IDs `h0`, `h1`, ...; data IDs `r1`, `r2`, ... . Cite data rows in stored metrics. Use the existing parser when header/span semantics are complex; do not guess row IDs or hashes. Preserve source HTML substrings as evidence, optionally adding human-readable row text to notes. Enumerate every applicable row/property pair in the candidate ledger.

Use minimal supporting spans plus any header, note or definition needed to interpret the assertion; discontinuous spans are allowed. Normalize spans as strings `"N"` or `"N:M"`, sorted with overlaps/adjacency merged. Never write `"N-M"` or `"116#r1"` into `source_line_spans`. Record exact, nonempty source substrings with original line IDs in `evidence`; an excerpt can support several independent metrics.

Preserve subject, value, comparator, unit, scale, frequency, scope, exceptions and negation. Keep decimal precision, inequalities, ± tolerances, scientific notation, percentages and ratios in source-faithful text. Do not invent zero, units or thresholds for absent data. For ratios written `N:1`, the contract's unit is `ratio`. Ranges additionally carry numeric `value_min`/`value_max`; other range types leave those fields null. Tolerances/approximations not losslessly expressible by the enum retain exact wording and interpretation notes; never rewrite them into different acceptance criteria.

**Bounds and comparators.** `metric_value` holds the bare number only, never a comparator (`100`, not `<100`). The comparator lives in `value_range_type` and in the source wording of `threshold_or_target`. Inclusive bounds (≥, ≤, 不小于, 不大于, 不低于, 不超过, 以上/以下 where the standard defines them as inclusive) use `lower_bound`/`upper_bound`. A **strict** bound (>, <, 大于, 小于, 低于, 超过) uses the same `lower_bound`/`upper_bound` and adds the reasoning tag `strict_bound`.

**`value_class = definition`** is for A5 rows only: a metric or formula definition, with `formula_or_definition` filled. Never use it for term definitions (X3) or applicability descriptors (X5).

**Conditions.** `condition` holds only applicability that the source states, in its words or a faithful paraphrase. Never infer a condition from context (for example "when a compliant treatment system is used" when the source says no such thing). Two things that look like conditions are not:

- **Suitability of a method or mode** ("适用范围: 人口密度高的农村地区"). It says where a mode is a good choice, not when the requirements of that mode apply; the mode itself belongs in `metric_subject`. Leave it out of `condition`. A real scope limit stated with a metric remains a condition of that metric; a scope limit of an excluded requirement (容积在50立方米以下的户用沼气池 for the NY/T 90 delegation) has no row to attach to and stays X5.
- **Measurement basis** (以烘干基计, 鲜样, dry basis, as received). It says how the value is measured. Put it in `metric_name` or `metric_desc` and keep it in `threshold_or_target`; not in `condition`.

**Schedules.** A frequency is a count per period. "每日/daily" is `exact`, `metric_value` `1`, `metric_unit` `次/日` (or `times/day`), with the source wording in `measurement_frequency`; "至少每日/at least daily" is `lower_bound`. Do not encode it as an interval of 1 day.

Match source language in core text fields. For English, leave `_en` fields empty/null. Translate non-English companion fields faithfully after checking the assertion. Categories are nonempty semantic keys, not paths: reuse existing keys through read-only lookup where appropriate; otherwise annotate an explained key locally without creating production categories or invoking indexing workflows.

Deduplicate repeated window detections using subject, property, value, unit, comparator, condition, claim class, table rows and provenance. Merge evidence for true repeats and retain `duplicate` ledger entries (D1). Do not deduplicate solely by name, number or line; different conditions stay separate. Preserve independently stated occurrences at different source locations for mention-level benchmarking and document that granularity. A vague restatement of a property that another row states concretely (a slogan "日产日清" beside "collected daily") is excluded under its X rule, not kept as a second row.

### 3.1 Statement kind

Every accepted metric carries exactly one reasoning tag `kind:<kind>` saying what the row is to a domain expert (ADR 2026100603). The application labels rows with the same vocabulary, so the gold kind is also the expected label.

| Kind | Rule and shape |
|---|---|
| `requirement_with_criterion` | A1 with `value_class` `requirement` or `target` |
| `requirement_value_open` | A4 (`limit_absent`, `value_class = metric-with-no-value`) |
| `test_parameter` | A6 (`test_condition`) |
| `metric_definition` | A5, and A1 interpretation cut-offs (`interpretation_bound`) |
| `metric_value` | A1 with `value_class` `observation` or `design_capability` |

The application's other kinds never describe an accepted row under these rules: `inspection_requirement` is X15, `delegated_requirement` is X16, a non-numeric `observation` is X15, a term `definition` is X3. Consequently no accepted row has `value_class = reference`, the tag `external_reference` or a `cited_doc:` tag, and the only accepted `qualitative` rows are A5 definitions.

`validate` derives the kind from `value_class`, `value_range_type`, `formula_or_definition` and the tags, using the same rules as the application, and refuses a row whose `kind:` tag disagrees. A disagreement means the row's representation is wrong (for example an interpretation cut-off stored as a requirement), not that the tag should be changed to match. `metric-with-no-value` exists only in the benchmark; the kind is derived from it exactly as from an `extract_metrics` row with `value_class = requirement` and `limit_absent`, so the two still match when scored.

### 3.2 Metrics with no value (A4)

An A4 row names a real metric whose value this document leaves open: to a supplier's declaration, to an agreement, or to be set or sized according to another factor or by design. Store it as a metric, not as a requirement:

- `value_class` is `metric-with-no-value`; for a non-English source, `value_class_en` is `metric with no value`. No other rule uses this class, and every A4 row uses it.
- `value_range_type` is `limit_absent`; `metric_value`, `metric_unit`, `value_min` and `value_max` stay empty. Do not move a typical value or unit into them: the document states none.
- `threshold_or_target` keeps the source's duty in its own words ("机器成肥设备应明确比能耗运行技术参数。"), readable on its own.
- `metric_desc` (and `metric_desc_en` for a non-English source) holds, in this order:
  1. **what the metric is**: the property, of which object, how it is measured or computed, and its usual unit ("比能耗：机器成肥设备每处理 1 t 易腐垃圾所消耗的电能，单位 kWh/t。");
  2. **typical values**, introduced by "典型值（领域经验，非本文件规定）：" or, in English, "Typical values (domain knowledge, not stated by this document):". Give a range and say what it depends on (equipment type, scale, feedstock). Use values a domain expert would recognise for this kind of object; if you are not confident of a range, say "no reliable typical value" rather than inventing one.

  This is the one field where knowledge from outside the source is allowed, and only in the marked typical-values part. `evidence` remains exact source quotes; the typical values are never evidence and never `confidence`.
- Write the reason for the A4 candidate naming how the value is left open: the party that must declare or agree it, or the factor it must be set or sized by. Put that factor in `metric_desc` too ("按垃圾日处理量确定"); it is not a `condition`, because it does not limit where the metric applies.

## 4. Audit completeness, correctness and consistency separately

Perform all three reviews against the source after drafting:

1. **Completeness:** re-read each section/table without relying on drafted metrics. Enumerate measurements/property requirements again; reconcile every candidate with final rows or an explained exclusion. Recheck conjunctions, cross-line clauses, continued tables, footnotes, formulas, header units, numeric words, inspection requirements and delegated requirements (each one an X15/X16 candidate, §2.4). Account for every data-row/property pair and all original lines.
2. **Correctness:** verify every saved field against cited lines. Check subject-to-value association, operators/negation, units/scales, row/column assignment, ranges/tolerances, frequency, applicability, translations and duplicates. In addition:
   - every accepted row passes the gate (§2.1) and its `rule_id` matches its `value_range_type`/`value_class` and tags;
   - every non-empty `condition` appears in the source (no invented applicability);
   - every `threshold_or_target` states the requirement on its own, readable without the row's other fields (not a fragment such as "种名");
   - `metric_value` holds no comparator; strict bounds carry `strict_bound`;
