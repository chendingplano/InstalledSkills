## Independence

Author the benchmark independently of `extract_metrics` predictions. Do not call the processor or preview extraction API, copy `kb.metrics`, or read its predictions until the benchmark is frozen. Production records are predictions, not ground truth. Do not inherit the older `document-metric-extractor` skill's precision-over-recall policy or legacy file/storage schema.

Recall and precision are both required. A benchmark that over-includes understates the extractor's recall exactly as one that under-includes overstates it. When in doubt, apply the gate (§2.1); do not include something just because it uses 应 ("shall").

## 2. Make a full-document candidate inventory

Read every source line, including appendices, tables, notes, equations and headings. For long documents use bounded windows with surrounding context, tracking which original line IDs have been read; return to complete evidence before deciding boundary-spanning assertions. Search is a second-pass discovery aid, never a replacement for reading the document.

Build two ledgers in the payload:

- `coverage`: non-overlapping source ranges covering every line, with section/table-specific review notes, including regions with no metrics.
- `candidates`: each plausible assertion with a stable local ID, exact spans, disposition (`accepted`, `excluded`, `duplicate`, or temporarily `uncertain`), **`rule_id`** (the rule below that decided it), rationale and final metric IDs. A single line/table can have many candidates; line coverage alone is insufficient.

`rule_id` must be one of the bold IDs in this file: an accepted candidate cites an `A` rule, an excluded one an `X` rule, a duplicate **D1**. The rationale says how the rule applies to this text.

### 2.1 The metric gate

A candidate is a metric only if the source names all three of:

- **(a) an object**: a thing, facility, vehicle, container, equipment, product, material, sample or test. An activity counts as the object only when the requirement is a number about it (for example "每月至少检查2次"); then record that the object is unspecified.
- **(b) a property of that object** that can be measured or inspected: a quantity, a physical or functional feature, a state, a frequency or duration, a count of the object's parts.
- **(c) a value, bound or concrete criterion** for that property, or one of the two stand-ins: an explicit delegation of the criterion to an **identified** document (A3), or an explicit statement that the value is set elsewhere or must be declared (A4).

Test the clause, not its keywords. Ask: "What would an inspector measure or look at, on which object, and what result passes?" If any of the three answers is missing from the source, the candidate fails the gate.

### 2.2 Accept rules

| Rule | Accept when | `value_range_type` / `value_class` |
|---|---|---|
| **A1** | A numeric value, bound, range or tolerance of a property of an object, including counts, frequencies, ratios and rates. Observations, targets and design capabilities keep their actual claim class. | numeric / as stated |
| **A2** | A concrete inspectable property requirement without a number: a physical or functional feature (bin has a lid; vehicle is fully enclosed; anti-leak), or a state whose presence or absence can be observed (no odour, no sewage, no litter, container intact and undamaged). | `qualitative` |
| **A3** | A requirement on a specific object that delegates its criterion to an **identified** document (standard number or exact title). See "Delegated requirements" below. | `qualitative` / `reference` |
| **A4** | An explicit statement that the value is left open: set by agreement, determined by another factor (volume set by daily throughput), or **to be declared** by a supplier for a named parameter (equipment shall state its specific energy consumption). Model the named parameter itself, never "clarity of the parameter". | `limit_absent` |
| **A5** | A metric or formula definition: an equation, or a definition of how a named measured quantity is computed. Keep the operands inside the formula row; they are not separate rows. | per value / `definition` |
| **A6** | A numeric test-method setting that affects the result (sample count or mass, solid:liquid ratio, shaker frequency and amplitude, extraction/settling/incubation time, temperature, extract volume, seeds per dish, number of replicates or blanks, storage time and temperature). Subject is the test or its sample; tag `test_condition`. | numeric / `requirement` |

### 2.3 Exclude rules

| Rule | Exclude | Examples |
|---|---|---|
| **X1** | An action people must take, or an instruction to residents or operators. | "drain before disposal", "cover the bin after use", "collect and transport separately" |
| **X2** | An organizational, administrative or planning duty: things go into a plan, someone inspects "regularly", publicity, training, responsibility assignments. | layout/scale figures go into county plans; 定期检查 |
| **X3** | A principle, slogan, policy aim or term definition (the definitions clause and "basic requirement" principles). A term definition is not A5 unless it defines how a quantity is computed. | 应收尽收, 日产日清, 四分四定 |
| **X4** | The structure of a classification scheme, such as the number of categories. | "分为四大类" |
| **X5** | Applicability: where or when a method suits, or the scope boundary of a cited standard. Carry a real scope as `condition` on the metric it limits. | "适用于人口密度高的地区"; "户用沼气池 ≤50 m³" as the scope of NY/T 90 |
| **X6** | A direction-only aspiration: a named indicator with no value or target level. | 提高分类准确率 |
| **X7** | Provision of a facility or system, or a disposal route, with no property of the facility. | "配备收集处理系统", "残渣有合理出路", "飞灰妥善处置" |
| **X8** | Permissive or weakened modality: 可 (may), 宜 (should, recommended), 鼓励/提倡 (encouraged), 尽量 (as far as possible). Only 应/必须/不应/不得 (and their English equivalents shall/must/shall not) create requirements. | 彩色标志颜色**可**按照 GB/T 19095 |
| **X9** | A delegation to an **unnamed** requirement ("达标排放", "meets safety requirements", "符合有关规定"), with no other criterion. If an identified document in the same clause covers the same property, that document's A3 row is the metric. | 烟气达标排放 |
| **X10** | Holding a licence, permit, qualification, certificate or documented provenance. This is a compliance check on a party, not a property of the object. | hazardous-waste licence; certificate of conformity; strain source stated |
| **X11** | A housekeeping or aesthetic state with no observable criterion. | 整洁, 美观, 良好, 卫生 (tidy, attractive, in good condition) |
| **X12** | A test-procedure step or apparatus identity, and qualitative test settings. Carry a qualitative setting (room temperature, in the dark) as the `condition` of the A6 row it qualifies. | "500 ml bottle", "fix vertically", "shake before analysis", "spread seeds evenly" |
| **X13** | Not a quantity of its own: formula operands split from their formula, a vague quality word with no criterion ("safe", "effective") when no concrete test is stated, or the bare name of a process. | germination rate and root length inside the GI formula |
| **X14** | Incidental numbers: years, edition numbers, document codes, clause numbering, page counts, coordinates, font sizes, standalone units, and normative-reference list entries. | |

**D1** marks a duplicate of a retained metric (see §3, deduplication).

A candidate that fails §2.1 but fits no X rule is not a reason to accept it. Keep it `uncertain` and resolve it before saving; if it reveals a gap in these rules, report it in `limitations` and do not save.

### 2.4 Delegated requirements (A3)

A clause imposing a requirement on a specific object while delegating criteria to a cited, identified document is a `qualitative` / `reference` row with `is_explicit_metric = false`, empty value/unit/formula, the original clause in `threshold_or_target`, `external_reference` and `cited_doc:<identifier>` tags, and identifiers in keywords. Do not import values from the cited document. A normative-reference list alone is excluded (X14). A numeric requirement citing only a test method remains an ordinary numeric metric (A1). A delegation with permissive modality is excluded (X8); one to an unnamed requirement is excluded (X9).

## 3. Resolve each assertion and its context

One row represents one property of one subject under one condition, with its stated value or requirement.

**Splitting.** Split a sentence only into parts that **each pass the gate (§2.1) on their own**. Split distinct properties ("anti-odour, anti-spill, anti-leak" are three inspectable features). Do not split a conjunction of vague adjectives into several rows; if the whole fails the gate, it is one excluded candidate. Never split formula operands from their formula. Split table cells/rows when conditions, objects or measured properties differ. Preserve a single interval/tolerance as one assertion. Never combine a value from one row with a subject/unit from another.

The subject is a source-supported object, facility, product, sample or test. If only an activity is named in a numeric requirement (for example, "每月至少检查2次"), use that activity as the subject and note that its object is unspecified. Do not attach it to a nearby object without evidence. If neither a subject nor activity can be established from the source/context, retain the candidate as uncertain rather than fabricating a subject.

For each table reconstruct multi-level headers, units, row labels, rowspans/colspans, captions, footnotes, merged cells and continued tables before annotating values. A whole HTML table may occupy one source line. Keep its line ID unchanged and record logical data row IDs in `source_table_rows`. Follow `ParseTableGrid` in `ChenWeb/server/api/doc-processing/table_grid.go`: header IDs `h0`, `h1`, ...; data IDs `r1`, `r2`, ... . Cite data rows in stored metrics. Use the existing parser when header/span semantics are complex; do not guess row IDs or hashes. Preserve source HTML substrings as evidence, optionally adding human-readable row text to notes. Enumerate every applicable row/property pair in the candidate ledger.

Use minimal supporting spans plus any header, note or definition needed to interpret the assertion; discontinuous spans are allowed. Normalize spans as strings `"N"` or `"N:M"`, sorted with overlaps/adjacency merged. Never write `"N-M"` or `"116#r1"` into `source_line_spans`. Record exact, nonempty source substrings with original line IDs in `evidence`; an excerpt can support several independent metrics.

Preserve subject, value, comparator, unit, scale, frequency, scope, exceptions and negation. Keep decimal precision, inequalities, ± tolerances, scientific notation, percentages and ratios in source-faithful text. Do not invent zero, units or thresholds for absent data. For ratios written `N:1`, the contract's unit is `ratio`. Ranges additionally carry numeric `value_min`/`value_max`; other range types leave those fields null. Tolerances/approximations not losslessly expressible by the enum retain exact wording and interpretation notes; never rewrite them into different acceptance criteria.

**Bounds and comparators.** `metric_value` holds the bare number only, never a comparator (`100`, not `<100`). The comparator lives in `value_range_type` and in the source wording of `threshold_or_target`. Inclusive bounds (≥, ≤, 不小于, 不大于, 不低于, 不超过, 以上/以下 where the standard defines them as inclusive) use `lower_bound`/`upper_bound`. A **strict** bound (>, <, 大于, 小于, 低于, 超过) uses the same `lower_bound`/`upper_bound` and adds the reasoning tag `strict_bound`.

**`value_class = definition`** is for A5 rows only: a metric or formula definition, with `formula_or_definition` filled. Never use it for term definitions (X3) or applicability descriptors (X5).

**Conditions.** `condition` holds only applicability that the source states, in its words or a faithful paraphrase. Never infer a condition from context (for example "when a compliant treatment system is used" when the source says no such thing).

Match source language in core text fields. For English, leave `_en` fields empty/null. Translate non-English companion fields faithfully after checking the assertion. Categories are nonempty semantic keys, not paths: reuse existing keys through read-only lookup where appropriate; otherwise annotate an explained key locally without creating production categories or invoking indexing workflows.

Deduplicate repeated window detections using subject, property, value, unit, comparator, condition, claim class, table rows and provenance. Merge evidence for true repeats and retain `duplicate` ledger entries (D1). Do not deduplicate solely by name, number or line; different conditions stay separate. Preserve independently stated occurrences at different source locations for mention-level benchmarking and document that granularity. A vague restatement of a property that another row states concretely (a slogan "日产日清" beside "collected daily") is excluded under its X rule, not kept as a second row.

## 4. Audit completeness, correctness and consistency separately

Perform all three reviews against the source after drafting:

1. **Completeness:** re-read each section/table without relying on drafted metrics. Enumerate measurements/property requirements again; reconcile every candidate with final rows or an explained exclusion. Recheck conjunctions, cross-line clauses, continued tables, footnotes, formulas, header units, numeric words and delegated requirements. Account for every data-row/property pair and all original lines.
2. **Correctness:** verify every saved field against cited lines. Check subject-to-value association, operators/negation, units/scales, row/column assignment, ranges/tolerances, frequency, applicability, translations and duplicates. In addition:
   - every accepted row passes the gate (§2.1) and its `rule_id` matches its `value_range_type`/`value_class` and tags;
   - every non-empty `condition` appears in the source (no invented applicability);
   - every `threshold_or_target` states the requirement on its own, readable without the row's other fields (not a fragment such as "种名");
   - `metric_value` holds no comparator; strict bounds carry `strict_bound`.
   Exact excerpt validity and high confidence do not prove semantic correctness.
3. **Consistency:** group candidates by source line and by `rule_id`. For every excluded candidate, check that no accepted candidate on the same line (or with the same wording elsewhere) relies on the reasoning the exclusion rejected, and the reverse. Equivalent clauses must receive the same rule. Resolve each conflict by re-deciding both candidates, not by editing rationales. Then compare the accepted count with the number of distinct gate-passing assertions you would expect from the document's structure; a set dominated by `qualitative` rows from prose 应 clauses is a warning sign to re-check X1, X2 and X7.

Describe concrete checks/findings in `completeness_review` and `correctness_review`; put the consistency findings in `correctness_review` under a "Consistency:" heading. Resolve all uncertain candidates; never relabel uncertainty as exclusion merely to pass validation. If parser damage, missing context, a rules gap or contract ambiguity remains, retain draft JSON and identify it in `limitations`. Do not publish an incomplete/unresolved set as a complete benchmark. Distinguish completeness within the line file from original-PDF coverage; image-only or omitted content requires a stated limitation and appropriate review.
